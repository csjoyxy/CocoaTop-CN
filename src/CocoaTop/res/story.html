The Story

朋友们，大家好！

这篇文章旨在解释 CocoaTop 中实现的一些耐人寻味的概念、这些概念背后的思考，以及应用本身的初衷。同时，至少对某些人来说，这也是一篇有趣的读物 ;)

在开始之前，我想感谢 Luis Finke 制作了 miniCode （可在 Cydia 中获取） – 一个极佳的 Xcode 替代品，它成为了我第一个 iOS 应用（也是我第一个 Objective C 应用）的集成开发环境。（嘿，如果你以为我是在 iPad 上纯手打完所有的代码，那你就错了。我甚至还用了 Theos，见鬼，好吧！但这并不是重点！）

更新：围绕 CocoaTop 最具争议的话题之一就是图标 ;) 。最初那个由我匆匆绘制的图标，几乎在每个论坛和博客上都沦为了批评的目标， 中文、韩文甚至一些印度论坛概莫能外。正在那时，@DylanDuff3 慷慨地为我提供了他自己设计的图标版本， 也就是现在所使用的这个。

现在，你可能会说 CocoaTop 的目的是替代原本的终端“top” – 但事实并非如此。首先，UNIX 终端本身就是一种信仰：每个 iPad 用户都必须安装一个终端， 否则就有可能被误认为是个呆子，或者更糟 – 搞文科的。而且，在 iPad 上运行“top” 总是能吸引人们的目光。因此 CocoaTop 背后的初衷其实是：我想创造一些美好精致的东西， 并在此过程中收获知识。如果你觉得它好用，那就太棒了！

在开发 CocoaTop 期间，我发现了一个叫 Jonathan Levin 的人写的一本书、一个网站和一个论坛。我真不知道自己之前怎么会错过这么精彩的东西。它给了我 极大的灵感启发，更不用说那些值得深思的海量糟糕源码了。多亏了 Jonathan 对隐藏和未公开 API 的深入讲解，这个版本的 CocoaTop 才得以实现实时的单进程网络统计！ 另外，如果你喜欢控制台工具和 SSH，不妨试试他为 iOS 和 Mac OS X 开发的 Process Explorer。

好了，接下来聊聊有趣的硬核事实：

★ CPU 使用率相加的总和不是 100%，而是核心数×100%。不仅如此，它甚至可以超过这个数值，而且当核心在全力做正经事（比如蛋白质折叠之类的重活）时，肯定会超过。CPU 超过 100% 并不是为了逗你开心， 而是源于 Mach 内核的一种调度策略，称为衰减使用率调度（decay-usage scheduling）。当一个线程获得 CPU 时间时，它的优先级会不断被调低：这保证了交互式任务能有极短的响应时间，因为交互式任务并不总是有很高的初始优先级，尤其是在性能较弱的移动平台上。运行中线程的衰减 CPU 使用率与获得的 CPU 时间成线性正比增加，并定期除以衰减因子（一个大于 1 的常数）。因此，进程的 Mach CPU 利用率是过去一分钟内（实际）时间的衰减平均值。由于计算的时间基准各不相同（因为进程可能是刚刚创建的），所有 %CPU 字段的总和就有可能超过 100%。这也是为什么安卓很逊的原因。另外还有 Java 的原因，Java 本身并不差，但是……放在移动端？

更新：你可能已经注意到，在旧版 CocoaTop 中，kernel task（pid 0）占用了大量的 %CPU，事实上它吃光了所有未使用的 CPU 算力。这是因为每个 CPU 核心都有一个内核线程， 在核心不用时将其暂停以节省电池电量，从而实际上占满了剩余的 CPU 周期。当你切换到进程详情的线程模式时，实际上可以找到这些线程：它们在状态列中会显示一个表示“空闲（idle）”的小写“i”。 新版 CocoaTop 不再将这些线程计入内核 CPU 使用率中。遗憾的是，在 64 位设备上，获取内核线程信息受到了很大的限制。

★ 大家都了解进程，但 Mach task 又是什么呢？它们其实是截然不同的东西。事实上，技术上完全可以在没有 BSD 进程的情况下创建一个 Mach task。Mach task 甚至可以在没有线程和内存的情况下被创建（啊，微内核的优美之处，我的最爱）。Mach task 没有父子关系，这种关系是在 BSD 层实现的。这仿佛意味着 BSD（或者更广泛地说，POSIX）更有道德伦理，但其实不然。在 UNIX 中，父进程比子进程活得更久反而是常态。而且，父进程实际上时刻盼着子进程死去，否则它们就会变成僵尸进程（zombie）。这也是我深爱纯微内核的原因。

更新：在 iOS 用户态下无法创建极简 task，因为对应的 API task_create() 已被移除。但是底层的内核函数 task_create_internal() 依然存在，并在启动 BSD 进程时创建一个 task。

★ 你可以通过向左滑动来终止进程，但这看起来有点残忍。我真正想干的是消灭僵尸进程，但不知道这是否符合 iOS 的设计哲学。

更新：其实，僵尸进程并不是一个真正的进程，而只是内核中针对一个已不存在进程的记录项。 所以你无法杀死它。保留它的唯一原因是为了提醒父进程该子进程曾经存在过，并保存子进程留下的所有零碎数据，比如退出状态码。当父进程最终读取了这些数据（或者父进程自身死亡）时， 僵尸进程就会消失。

★ 根本不存在正在运行的“进程”这种东西，因为真正在跑的是线程，而不是进程。那么为什么会有一个“进程正在运行”的状态呢？嗯，这样做是为了简化输出展示，而且这实际上是直接沿用了原版“top”的源码实现。大多数进程状态都是根据线程状态按照简单的优先级规则推算出来的：也就是说，如果至少有一个线程在运行，进程状态就被认定为“R”，以此类推。完整的状态列表可以在列说明中查看：只需在列管理界面中轻点“Process state”项旁边的 (i) 即可。

★ 还有一列叫作“Mach Actual Threads Priority”。它实际包含的是进程内线程的最高优先级。原版“top”也是这样工作的。此外，Mach 支持多种调度机制，但在 iOS 中实际只使用了其中一种 – “时间片轮转（Time Sharing）”。另外两种机制“Round-Robin”和“FIFO”如果在这一列中出现，将分别以前缀 R: 和 F: 标出，但我从未见过它们。我出于好奇加上了这些标记 - 欢迎给我写信。

更新：Round-robin 轮转调度实际上在整个系统中被某些特定线程所使用，尤其是内核线程。 事实上，所有内核线程默认都采用轮转机制：不信你可以自己去看看！（如果你有幸能查看到 kernel task 详情的话）

★ 苹果在每个 iOS 新版本中都在不断收紧安全性，因此在 iOS 8 上 CocoaTop 已无法再显示 task 0 （kernel task）的详情。如果你还在用 iOS 7，你仍然可以享受到这些数据！其实，要是 iOS 没有塞满后门的话（至少在 v.7 中是这样 ;) ），它完全可以被称作有史以来最安全的公开平台。不过话说回来，总比另一家“不作恶”的公司好多了 ;)

更新：看来有关 kernel task 的详情在某些平台上可用，而在另一些平台上不可用。 这可能取决于所使用的越狱方式。我很高兴地通知大家，在运行 iOS 9 的某些设备上，这项信息又重新可以查看了！

★ 还有一个“Mach Task Role”列，它实际上显示的是为图形界面应用分配的角色，就像在 OS X 中那样。我注意到这只在 iOS 8+ 上有效。
